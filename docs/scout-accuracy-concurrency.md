# 累積精度APIの競合対策とページ切り替え

## 調査と安全境界

2026-10-19開始、10-20に測定完了。開始時のmainとfetchしたorigin/mainはともに `f204281f7165f75dc67b0a03bb9bfd5b6bd522cc`。未コミット変更なし。

対象は `scout-accuracy-cache.ts`、`bottom-scout-accuracy.ts`、`scout-accuracy-io.ts` と既存保存・評価処理。I/Oバッチは16件以内・順序維持・開始済み処理の完了待機という既存仕様を維持した。採点、重み、的中定義、営業日・revision選択は変更していない。

実利用者のDATA_DIR、環境設定・秘密情報は読んでいない。実データへの書込、J-Quants追加取得、MemWal送信、Sui操作、LLM利用なし。検証データは独自生成した一時fixtureのみ。

## 確認した問題と対策

最初に4つの再現テストを追加し、修正前はすべて失敗した。

- 同じキーの同時リクエストが独立して集計する。Service・分析条件ごとに進行中Promiseを共有し、成功・失敗のどちらでも取り除く。
- `store.read` のメモがファイル名だけをキーにしており、欠損ファイルの `null` と `[]` が混同される。物理読込の結果またはENOENTだけを共有し、欠損時のfallbackを呼出ごとに適用する。存在するファイルをfallbackの違いだけで重複読込しない。
- 計算途中のファイル追加を検出しても、キャッシュしないだけで古い結果を返す。計算結果の内容hashと一覧を照合し、不一致なら最初から再計算する。最大3回で安定しなければエラーとし、成功結果を返さない。
- 計算後の内容再検証がなく、同名ファイルの改変を見逃す。キャッシュ利用・新規計算の両方で、内容照合を2巡、一覧照合をその前後に行う。

追加で、一覧取得の進行中Promiseもprefixごとに共有する。並行した一覧取得が異なる世代を返して、最後の取得で先の証拠を置き換えることを避ける。

評価保存を伴う集計は既存Storeのプロセス間writer lock内で行う。評価原本は一旦メモリに保留し、入力照合の成功後にimmutableで保存する。保存先に別内容があれば拒否し、保存後も再照合する。失敗した読み取りsnapshotの保留評価を保存しない。予測原本はこの経路から書き込まない。読み取り専用診断ではlockやwriteを行わない。

キーには記録区分・保存可否・アプリモード・市場環境分類用コードを含む。異なるService間でPromiseやキャッシュは共有しない。同じ保存先に接続する別Serviceの書込はStore lockで直列化する。取得締切が逆行した場合や、保存済みの未来データ・営業日締切が到来した場合は、古い計算を共有しない。

大規模計測中に、初回計算が60秒を超えると応答前にTTLを消費し、実時間が進むページ操作では常に再計算する問題も確認した。固定cutoffの負荷試験だけでは発見できないため、120秒の計算時間を模したAPIテストを先に追加し、修正前は系列が再構築されることを確認した。TTLは計算・整合性検証・必要な保存の完了から最大60秒とし、予測の評価cutoff自体は変更しない。元データにある未来の利用可能時刻・営業日締切が先に到来する場合は、そちらを優先して失効する。アクセスのたびに期限を延長する仕組みではない。

## ページと累積集計の分離

全履歴の重複除外、TOP3/5/10、スコア帯・市場環境別成績を1回計算し、計算完了から最大60秒のメモリキャッシュに保持する。ページ番号・ページサイズ・reportIdは明細選択にだけ使う。ページ切り替えでも全原本の照合は省略せず、変更がなければ系列再構成・全履歴の再評価・再集計を省略する。

返すページの予測だけを複製し、振り返りを生成する。キャッシュの全履歴データは呼出元に直接渡さない。表示順・全履歴で最初の重複採用・累積件数・将来作成された予測の除外を維持する。候補0件の分析もページ件数には含む。

## 性能試験の条件

`scripts/benchmark-scout-concurrency.ts` は基準mainの3モジュールを比較対象として取り込み、現実寄りの人工fixtureだけで両実装を測る。1分析10候補、250人工銘柄、1営業日2revision、4つの基準日、各分析の保存評価を持つ。これは保存・集計負荷用の合成値であり、実市場の精度や時点ごとの分析アルゴリズムのバックテストではない。

fixtureは高速生成用のコンパクトJSON、短い人工revision ID、全日openの人工カレンダーを使う。実保存データのバイト量や、多様な営業日にわたる実市場履歴と同じ負荷上限を保証するものではない。

各規模3反復。新Serviceでの初回、同一ページ再表示、ページ2・3への連続切り替え、別の新Serviceに同時2リクエストを測る。新ServiceはアプリキャッシュなしだがOSキャッシュは消去しない。ネットワークは禁止し、測定中に回帰テストを並行実行しない。固定されたfixture時刻を使うので、有効期限内のキャッシュ再利用を測る。実時間が進む場合の長時間初回計算と未来データ境界は別のAPI回帰テストで確認する。ページを開いたまま60秒以上待った後の再計算時間はキャッシュhitの値ではない。

時間はAPIが呼ぶ関数の完了までで、HTTP・ブラウザ描画は含めない。p50/p95はnearest-rankであり、3回のp95は最大値。メモリはGC後のRSS/heap差分と10ms間隔のRSS最大増分。ファイル読込回数・バイト数はNode readFileの実測で、物理ディスクI/Oとは異なる。応答サイズはUTF-8 JSONバイト数。

性能試験は `persist:false` で、保存済み評価がある履歴を集計する。新規評価原本のfsync時間・実運用writer lockの待機・HTTP認証は測定対象外。同時保存の安全性は別の小規模回帰テストで確認した。年度をまたぐ多様な基準日、比較指標の大量データ、長期の実市場系列の性能もこのfixtureだけでは検証できない。

生測定はE2Eが初期化するtest-resultsとは分け、無視対象の `node_modules/.cache/scout-concurrency-<timestamp>.jsonl` へ逐次保存する。比較用ソース・生成原本・測定JSONはコミットしない。

比較用に `git show f204281:apps/api/src/{bottom-scout-accuracy,scout-accuracy-cache,scout-accuracy-io}.ts` の3ファイルを取得し、相対importだけをローカル比較用の絶対file URLに変換する。3ファイル相互のimportは取得した基準版同士、それ以外はこのチェックアウトの既存モジュールを使う。比較用ディレクトリのpackage.jsonは `type: module` とする。アルゴリズム・評価関数・保存形式は変更していない。

```text
rtk proxy node --expose-gc --max-old-space-size=8192 --import tsx scripts/benchmark-scout-concurrency.ts 1000,5000,10000 node_modules/.cache/scout-accuracy-baseline/bottom-scout-accuracy.ts 3 both
```

最後の引数は `both` / `baseline` / `improved`。同一プロセスのbothでは、各ページと同時呼出の応答hashも前後で照合する。単独variantの実行だけでは前後一致を検証済みとは扱わず、別途基準ログとの照合が必要。今回は最終版を独立実行し、5,000・10,000分析の保存済み応答hashを基準ログと事後照合した。

## 制約

全履歴の内容照合は引き続きO(履歴数)。改変検出を省略した高速化ではない。検証を2巡にしたため、同一ページのキャッシュhitでも読込量は増える。全履歴の候補をメモリに保持するので、ページ切り替えのCPU削減と保持メモリにはトレードオフがある。

JSONファイルシステムに複数ファイルの原子的snapshot機能はない。アプリのwriter lockを守る書込は直列化し、それ以外の手動編集・削除は複数回の内容・一覧照合で検出する。ロックを無視する外部プロセスの任意のタイミングでの変更や、変更直後の完全な書き戻しをトランザクションとして防ぐ保証はない。安定しない入力は拒否して再試行を案内する。Store lockの既存待機上限120秒も維持する。

保存を有効にした集計はwriter lockを保持するため、大規模履歴では別ジョブ・workerが待機上限に達する可能性がある。今回の性能値はその待機を含まない。プロセスをまたぐ集計キャッシュの共有も行わず、保存のlockだけを共有する。

実データ精度、HTTP認証経由の大量負荷、実機iPhone描画、実J-Quants・MemWal・Sui接続は今回未検証。
