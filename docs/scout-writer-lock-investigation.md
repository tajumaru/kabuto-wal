# 累積精度APIのwriter lock調査

## 範囲

2026-10-20、`origin/main` / `main` の `66208f5` を調査。開始時の未コミット差分なし。終了前にもfetchして同じmainを確認した。本変更は計測スクリプト・再現テスト・調査記録のみ。製品コード、予測方式、保存形式は変更していない。

実データ・設定・秘密情報を読まず、J-Quants / MemWal / Suiに接続していない。fixtureはOS一時ディレクトリだけに作成し、終了時に削除した。これは精度検証でも実運用性能の保証でもない。

## ロックの仕様と原因

- `packages/storage/index.ts` の `Store.lock(fn, waitMs = 120_000)` は保存root共通の `.writer-lock` ディレクトリをatomic mkdirで取得する。別Service・別プロセスでも同じrootなら排他となる。ファイル単位ではない。
- 取得待ちは25ms間隔。120秒は**取得の待機上限**で、callbackの実行時間上限ではない。保持時間の制限・lease・heartbeat・公平な待ち行列はない。
- `owner.json` のPIDが死んでいる場合（ESRCH）は除去して再取得する。生きたPIDや所有者情報を読めない場合は待機し、上限で例外になる。
- `Store.write` 自体はこのロックを取得しない。今回の競合writerは、既存の協調的書き込みと同じ `other.store.lock(() => other.store.write(...))` を使用した。単独のwriteや手動ファイル編集まで排他する仕組みではない。
- `scout-accuracy-cache.ts` は `writeLock=true` の場合、集計・キャッシュ検証・保存・保存後再検証をまとめて `s.store.lock(resolve)` 内で実行する。
- `bottom-scout-accuracy.ts` の通常GETは保存有効が既定。同一Service・同一キーは進行中Promiseを共有するが、別Serviceは共有しない。評価原本が既に存在して保存0件でも、初回とキャッシュ確認でroot lockを取得する。
- 内部呼び出しの `{persist:false}` はロックを取得しない。通常GETのqueryでこのオプションを切り替える仕様ではない。

## 計測方法

`scripts/benchmark-scout-writer-lock.ts` を明示実行する。importだけでは実行しない。既存の `scoutScaleFixture` を再利用し、実環境の初期化はしない。fetchは禁止する。

```powershell
rtk proxy node --expose-gc --max-old-space-size=8192 --import tsx scripts/benchmark-scout-writer-lock.ts 1000,5000,10000
```

各規模10候補/分析、250銘柄、日足2revision、重複する4基準日の人工データ。既存評価1件だけをfixture内で除去して初回に保存させ、その直後にキャッシュ確認を行った。これはJSON保存負荷のfixtureで、独立した予測標本ではない。

計測用Serviceインスタンスのlock/writeをラップしただけで、ロック実装や待機上限は変更していない。ロックcallback開始時に別Serviceの通常writerを起動する。writerは無関係の `jobs/lock-probe.json` にだけ書くため、精度入力の変更を起こさない。待機には既定の120秒を使用した。

環境: Windows、Node v24.14.0、Intel Core i5-10400 2.90GHz、論理12CPU、RAM約31.7GiB。各区間1回、アプリキャッシュは初回cold・次回warm。OSキャッシュは消去していない。他ベンチマークやテストは測定と並行実行していない。p50/p95は未測定。

## 実測

単位は秒。保持時間は**ロックcallbackの開始から終了まで**で、ディレクトリ取得・owner書き込み・解除のFS処理は除く。実際の他writerの待機も併記する。

| 分析原本数 | 初回API全体 | 初回ロック内 | 他writer待機 | 他writer結果 | 保存0件のキャッシュ確認ロック内 | その間の他writer待機 |
|---:|---:|---:|---:|---|---:|---:|
| 1,000 | 30.663 | 30.656 | 30.682 | 保存成功 | 4.809 | 4.833 |
| 5,000 | 133.411 | 133.406 | 120.004 | タイムアウト、保存未実行 | 17.662 | 17.667 |
| 10,000 | 264.984 | 264.977 | 120.010 | タイムアウト、保存未実行 | 33.909 | 33.948 |

初回の保存はすべて評価原本1件。ロック内の区間内訳:

| 分析原本数 | 保存開始まで（計算＋保存前検証） | 実際のStore.write | 保存終了後（再検証等） |
|---:|---:|---:|---:|
| 1,000 | 25.832 | 0.005967 | 4.817 |
| 5,000 | 115.497 | 0.010781 | 17.898 |
| 10,000 | 231.272 | 0.005808 | 33.699 |

最大観測値は10,000分析のロック内264.977秒（約4分25秒）。初回の計算と保存前検証は公開関数の外側から独立計測できず、合算で記録した。Store.write時間だけに短縮できるという意味ではない。キャッシュ確認には保存が全くなくてもロックが必要になっている。読み取り・検証が占有の主因であり、書き込み時間の短縮や待機上限の延長だけでは解消しない。

詳細のJSONLは実行時に `node_modules/.cache/scout-writer-lock-<timestamp>.jsonl` に出力する（測定ログ・fixtureはGitに追加しない）。今回のログは `scout-writer-lock-1792440960526.jsonl`。

## 推奨する次の修正（今回は未実装）

1. cutoffを固定し、内容hash・欠損状態・入力ファイル一覧を記録して、重い読み取り・計算・評価の仮生成をロック外で行う。原本には書かない。
2. 保存0件の場合は、現在の内容・一覧検証を維持した上でroot writer lockを使わず返す。
3. 保存が必要な場合だけlockを取得し、記録した**全入力の内容と一覧**を保存直前に再検証する。世代・mtime・サイズだけの照合に置き換えない。
4. 競合時は保存せずロックを解放して、上限付きでロック外再計算するか、安全に拒否する。計算全体をロック内で再試行しない。
5. 同一評価が先に保存されていた場合はID・内容hash・参照先を検証する。同一なら再利用し、矛盾する原本は上書きせず拒否する。
6. 保存後の整合性確認とキャッシュ公開条件、待機期限を跨ぐ評価時刻、複数Serviceでの同時保存、原本変更・削除・追加を改めて検証する。成功するまで未検証の結果をキャッシュしない。

## リスクと未検証

- 二段階方式の保存前検証にも全原本の読み取りが残るため、保持時間がゼロになるとは限らない。変更検出を省かず、修正後に同条件で再計測する必要がある。
- 非協調的な書き込みはStore.lockを迂回できる。内容・一覧の再検証は必須だが、任意の手動編集に対するファイル群のatomic snapshot保証とは異なる。
- 複数Serviceでは初回計算が重複し得る。二段階化でCPU・I/O負荷が増える可能性があるため、誤った条件共有を避けつつ負荷を測る必要がある。
- 5,000・10,000分析で協調的writerのタイムアウトを再現した。実際のジョブがその例外から再開できるかはジョブごとの確認が必要で、今回の結果だけでデータ消失を断定しない。
- 実データ、実HTTP負荷、別プロセス競合、長期運用、修正後性能は未検証。実験対象は別Service同一プロセス。
- 製品コードを変えていないため、今回のコミットだけでは待機問題は解消しない。調査結果の確認後に修正を進める。
