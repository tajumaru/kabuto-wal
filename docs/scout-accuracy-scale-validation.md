## 診断・統計の定義

- 対象0件は `availability=no-predictions`、`message=検証対象なし（精度0%ではありません）`。アクセス不可・不整合の場合はunconfirmed・counts=null。
- 全履歴から同一方式・銘柄・基準日の最初の予測だけを採用。DEMO、研究、当日基準の区分は混ぜない。
- 的中は期限後の調整終値リターン0%超。待ち・不能を分母に入れない。
- Wilson 95%区間は独立な二項標本を仮定した参考区間。銘柄・連続日・重複期間の相関は補正していない。将来の上昇確率ではない。
- 対象は保存されたスカウト候補だけであり、非候補や市場全体の無作為標本ではない。選択バイアスを明示する。
- 予測当時の入力revisionと評価cutoffのrevisionを区別する。現在の価格で予測根拠を作り直さない。
- リターンは取引費用・配当・約定を含む実際の売買利益ではない。平均リターンと同一評価可能ペアの超過リターンを区別する。

## 性能測定の方法

`scripts/benchmark-scout-accuracy.ts` を使用。数値引数だけを受け取り、独自に作成した一時ディレクトリに人工履歴を生成する。実DATA_DIRを指定する機能はなく、ネットワーク呼び出しは禁止。生成JSONと生測定ログはコミットしない。

```text
rtk proxy pnpm exec tsx --expose-gc scripts/benchmark-scout-accuracy.ts 100,1000,5000,10000 3
```

Windows x64 / Node v24.14.0 / Intel Core i5-10400 2.90GHz（12論理CPU）/ RAM 34,078,408,704 bytes。前後で同じ機械・同じfixture生成方式。共有PC上での測定であり、厳密に隔離された性能試験ではない。

各規模で3回、アプリの集計キャッシュなし→同一ページのキャッシュ利用→ページ2への初回切替を測る。coldは新しいServiceによる**アプリキャッシュミス**であり、OSのファイルキャッシュは消去していない。評価cutoffは固定し、毎回同じデータで比較する。p50/p95はnearest-rank、3標本のp95は最大値なので、精密な裾分布の推定ではない。

固定した評価時刻で再呼び出しているため、キャッシュ利用値は有効期限内の再利用を測ったもの。実運用で操作間隔や長い初回処理によって最長60秒のTTLを過ぎる場合、同じ応答時間になるとは保証しない。

測定対象は累積精度APIが呼ぶscoutAccuracy関数の完了時間。HTTP、ブラウザ描画、レスポンスのJSONシリアライズ時間は含めない。レスポンスのUTF-8バイト数は別計測する。file readはNode fs.readFileの実呼出し成功数と読込payloadバイト数で、OSキャッシュを除いた物理ディスクI/Oは未計測。ディレクトリ列挙回数も別に記録する。

メモリは各測定前GC後から終了までのRSS/heapUsed差分と、10ms間隔標本のRSS最大増分。負値はメモリ回収を意味する。標本間の瞬間ピークや全システムのメモリ使用量は保証しない。

人工履歴は1分析原本に1候補、25人工銘柄・4つの重複する基準日、各原本に保存評価1件（初期seed原本1件も件数に含む）。意図的な重複予測を含む。全営業日openの人工カレンダーで、実際の市場成績・営業日ではない。特徴量値は保存負荷検証用の合成値であり、各基準日で予測アルゴリズムを再実行したバックテストではない。最大10候補/分析や長期の多様な実市場履歴より軽い負荷であり、実運用の上限性能とは扱わない。

## ボトルネックと変更

改善前1,000件で、初回約7.1秒・キャッシュ利用約2.9秒・ページ切替約7.1秒を確認した。内容hash検証のため毎回3,026ファイルを読み、ページ別のキーでは切替時に全集計を再計算する。

必要最小限の対策として、スカウト精度検証内だけに16件以内の並列読み込みを適用した。キャッシュのファイル一覧・内容hashの照合は毎回維持。集計前に予測順を元の順序へ整列し、重複採用・浮動小数点の加算順・表示順位を維持する。バッチ内で失敗した場合は開始済み処理を待ってから失敗を返す。

全原本の検証を省略するTTL/世代番号だけのキャッシュや、改変を見逃す派生索引は導入しない。予測・評価原本を上書きせず、新DB・有料サービス・SDK変更もない。読み込み回数自体を減らす変更ではなく、独立したI/O待ちを重ねる改善である。

## 整合性・回帰

改善後の100・1,000・5,000・10,000件すべてで、同じキャッシュを使い、原本追加による件数増加、hash不一致改変の拒否、予測manifest削除による件数減少を検証し成功した。小規模の自動テストでは評価原本改変と参照先分析原本の欠損も拒否し、診断でファイルが増減しないこと、ネットワーク呼出し0を確認する。

16件の並列上限、入力順の保持、失敗時に開始済み処理を待つこともテストした。

- `pnpm lint`：成功。初回に見つかった未使用初期代入を除去して再確認。
- `pnpm typecheck`、`pnpm build`：成功。
- `pnpm test:e2e`：終了コード0、`.last-run.json` はpassed / failedTests=[]。
- `pnpm test`：大規模測定の整合性チェック・E2Eとの同時実行時は、既存 `kabumaru-agent-walk-forward.test.ts` の1件が240秒でタイムアウト（216成功・1失敗）。他の負荷試験終了後、同じ全テストを再実行して75ファイル・217件すべて成功、199.85秒。タイムアウト閾値・テスト内容は変更していない。負荷競合は疑われるが、単一要因と断定しない。既存の重いテストの性能安定性は残る課題。

旧形式研究計画の実行禁止・MemWal削除抑止・Sui関連を含む既存回帰はfixture/モックで確認。実J-Quants・MemWal・Suiのネットワーク動作や署名・送信は未検証。
